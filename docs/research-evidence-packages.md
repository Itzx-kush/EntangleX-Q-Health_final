# Research Evidence Packages

## Purpose

A Research Evidence Package is an immutable, machine-readable manifest of the
persisted evidence associated with one experiment. It lets a researcher inspect
what was evaluated, which evidence records exist, what is missing, and how the
evidence traces back to datasets, runs, models, studies, protocols, and
artifacts.

Package creation only reads persisted metadata. It does not train a model,
rerun an evaluation, regenerate quantum execution, or recompute a scientific
study.

## Architecture

`ResearchEvidencePackage` is an immutable snapshot owned by an `Experiment`.
The row stores the package status, deterministic package fingerprint, governing
configuration fingerprint, evidence inventory, provenance, limitations,
evidence gaps, and canonical manifest.

The existing Artifact registry remains the canonical artifact mechanism. Every
package has one immutable `research_evidence_package` metadata artifact with
`application/json` content. No second artifact store, report system, Model Card,
comparison engine, or verified-demo mechanism is introduced.

Repeated creation for the same evidence state returns the existing package and
artifact. When persisted evidence changes, a new package and artifact are
created; prior snapshots are not modified.

## Package schema

Schema version: `research_evidence_package_v1`.

The top-level contract contains:

- package identity, status, fingerprint, and governing configuration fingerprint
- experiment identity and status
- immutable dataset/version identity and content hash
- model, run, model-artifact, and Model Card references
- source context (`live_run` or `verified_demo_experiment`)
- structured evidence inventory
- provenance and integrity references
- explicit limitations and evidence gaps

Large scientific payloads are not copied into the package. Existing studies,
protocols, cards, and artifacts are referenced by ID, fingerprint, and integrity
hash. Persisted held-out metrics are included as a concise aggregate evaluation
summary.

## Evidence inventory

Each category records an availability status, record count, referenced IDs,
artifact IDs, latest compatible record, evidence timestamp, source
fingerprints, limitations, and an availability reason.

Categories:

- evaluation
- multi-seed studies
- external validation
- distribution shift
- group-aware validation
- calibration
- threshold analysis
- robustness
- ablation
- quantum diagnostics
- controlled comparison
- Model Cards
- explainability

Availability values are `available`, `not_available`, `not_applicable`,
`limited`, `incomplete`, and `blocked`. Availability is derived only from
persisted records, never from frontend state, model configuration, or the
existence of an action button.

## Completeness semantics

- **READY** — core and applicable optional evidence is available and internally
  consistent.
- **PARTIAL** — core evidence is packageable, but optional evidence is missing
  or limited.
- **INCOMPLETE** — meaningful core evidence such as a model, persisted
  evaluation, immutable dataset version, or live-run provenance is missing.
- **BLOCKED** — identity, provenance, configuration, or artifact-integrity
  checks failed. A package is not created.

Status is not a model-quality score, ranking, or superiority claim.

## Fingerprints and immutability

The package fingerprint is SHA-256 over canonical JSON containing the schema
version and stable evidence identity, including experiment state, dataset and
version hashes, model and run IDs, model artifact hashes, evidence record and
artifact IDs, evidence artifact hashes, study/protocol fingerprints, and source
context.

Timestamps generated by package persistence and presentation-only fields are
excluded. The same evidence state and schema produce the same fingerprint.
Changed evidence produces a new fingerprint and immutable snapshot.

The governing configuration fingerprint reuses a persisted `Run`
fingerprint when one consistent value exists. Legacy experiments fall back to a
canonical fingerprint of the persisted experiment configuration. The preflight
blocks conflicting live-run configuration fingerprints.

## Preflight and integrity

Preflight checks:

- experiment and archive state
- dataset and dataset-version identity
- model, run, and evidence ownership
- model/dataset and run/dataset consistency
- study and artifact ownership
- Model Card and quantum-diagnostic model ownership
- controlled-comparison experiment ownership
- live-run configuration-fingerprint consistency
- verified-demo source semantics and available manifest integrity

Preflight is read-only and returns feasibility, candidate status and
fingerprint, inventory, blockers, warnings, missing evidence, and the candidate
manifest. Critical failures return `package_blocked` from creation without
persisting a package.

## Verified demonstrations

Verified demonstrations use `source_context.type =
verified_demo_experiment`. Their precomputed status, package artifact version,
manifest SHA-256, dataset hash, and model artifact hashes are preserved when
available. No synthetic `Run` is created, and the package never claims that the
evidence came from a live training execution.

`GET /api/experiments/{id}/verified-evidence` remains unchanged. A Research
Evidence Package references the same provenance but does not replace that
endpoint.

## Model Cards and controlled comparisons

Existing Model Card artifacts are referenced by model ID, artifact ID, schema
version, card status, and integrity hash. Missing cards are explicit optional
evidence gaps; package creation does not fabricate a card.

Existing `ControlledComparisonProtocol` rows are referenced by protocol ID,
schema/status, configuration and protocol fingerprints, model-pair identities,
artifact ID, and limitations through the inventory. The package does not rerun
comparison logic or rank classical and quantum models.

## Privacy and security

Packages may contain aggregate metrics, counts, safe configuration metadata,
IDs, hashes, fingerprints, provenance, and study references.

Packages never include raw CSV content, biomedical rows, patient identifiers,
direct identifiers, uploaded records, credentials, access tokens, secrets,
environment variables, or raw filesystem paths. Error responses use the
application's safe error envelope.

## API

- `POST /api/experiments/{id}/evidence-package/preflight` — read-only preflight
- `POST /api/experiments/{id}/evidence-package` — create or return the current snapshot
- `GET /api/experiments/{id}/evidence-package` — latest snapshot
- `GET /api/experiments/{id}/evidence-package/{package_id}` — specific snapshot
- `GET /api/experiments/{id}/evidence-package/{package_id}/provenance` — provenance and integrity
- `GET /api/experiments/{id}/evidence-package/{package_id}/download` — canonical JSON download

The existing experiment report endpoints remain the human-readable export.
Research Evidence Packages complement reports as canonical evidence manifests.

## Frontend

Experiment detail contains a compact **Research Evidence Package** section. It
shows status, package identity, fingerprint, source context, artifact integrity,
category availability, limitations, and gaps. Researchers can generate or
refresh the current snapshot, inspect the structured package, and download JSON.

## Scientific limitations and non-claims

A Research Evidence Package is a research-evidence manifest. It is **not**:

- clinical validation, diagnostic proof, or treatment evidence
- regulatory approval or deployment readiness
- population-wide effectiveness or generalization
- statistical significance unless a referenced implemented test establishes it
- evidence of quantum advantage or quantum-model superiority

The package reports persisted evidence and its limitations. It does not
reinterpret that evidence into a winner.
